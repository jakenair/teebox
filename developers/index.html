TeeBox Seller API

Build a listing tool that posts, updates and ends golf listings on TeeBox for the sellers who connect it. JSON over HTTPS.

The sandbox is open. We issue test keys by hand: contact us with your tool's name. The live API is not open yet, so live keys are refused.

EnvironmentBase URLKeysStatus
Sandboxhttps://us-central1-teebox-market.cloudfunctions.net/sellerApi/v1pk_test_... sk_conn_test_...Open, keys on request
Livehttps://api.teeboxmarket.com/v1pk_live_... sk_conn_live_...Not open yet

Your keys choose the environment: test keys always use the sandbox, live keys always use live. The sandbox holds only fake sellers and listings, kept apart from the real ones.

How the sandbox differs

  • Listings have no public page, so url is null. Nobody can buy them, and no emails are sent.
  • Photo URLs are checked for shape only and returned as you sent them. Nothing is downloaded.
  • Text isn't moderated. Put sandboxviolation in the text to test content_violation.
  • Use the sandbox sell call to test how your tool handles a sale.

Quickstart

  1. TeeBox approves your tool and issues a partner key.
  2. You get a connection key for a seller. In the sandbox, TeeBox sends you one for a fake seller. On live, the seller opens Profile, Connected tools in TeeBox, picks your tool, and pastes the key into it.
  3. Check the connection, then create a listing.
export TEEBOX=https://us-central1-teebox-market.cloudfunctions.net/sellerApi/v1
export PARTNER_KEY=pk_test_your_partner_key
export SELLER_KEY=sk_conn_test_the_sellers_key

curl "$TEEBOX/me" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" \
  -H "Authorization: Bearer $SELLER_KEY"
curl -X POST "$TEEBOX/listings" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" \
  -H "Authorization: Bearer $SELLER_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: your-sku-1001" \
  -d '{
    "title": "TaylorMade Qi10 Driver 10.5",
    "brand": "TaylorMade",
    "category": "driver",
    "condition": "Very Good",
    "price": 249.99,
    "quantity": 1,
    "description": "Light marks on the crown.",
    "specs": {"model": "Qi10", "loft": "10.5", "flex": "S", "dexterity": "RH"},
    "photo_urls": ["https://example.com/driver-1.jpg", "https://example.com/driver-2.jpg"]
  }'

Keys

Every request needs two keys.

  • Partner key, in X-TeeBox-Partner-Key. It identifies your tool. Keep it on your server.
  • Connection key, in Authorization: Bearer. A seller creates one for your tool. It only works with your partner key.

Sellers can disconnect at any time, and connecting again replaces the old key. TeeBox can pause a partner; its connections then stop on the next request. A test key and a live key can't be used together.

Sellers confirm for themselves. A seller must confirm they are 18 or older and agree to the Seller Terms once, in TeeBox. Your tool can't do it for them. Until they do, creating a listing returns seller_consent_required.

Endpoints

Every response is JSON with a request_id, also sent as X-Request-Id. The examples use the variables from the quickstart.

GET /v1/me

Which environment, partner and seller this connection belongs to. Check seller.can_list before you post; when it is false, show cannot_list_reason.message to the seller. listings_created_today counts the current 24-hour window.

curl "$TEEBOX/me" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" -H "Authorization: Bearer $SELLER_KEY"

GET /v1/categories

Categories, the spec fields for each, the allowed values and the listing rules. Read it at startup and refresh it daily rather than hard-coding values.

curl "$TEEBOX/categories" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" -H "Authorization: Bearer $SELLER_KEY"

GET /v1/listings

All of the seller's listings, including ones not made by your tool, oldest change first. Optional: updated_since, status (comma-separated), limit, cursor. See Keeping in sync.

curl "$TEEBOX/listings?updated_since=2026-12-01T00:00:00Z&limit=100" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" -H "Authorization: Bearer $SELLER_KEY"

POST /v1/listings

Create a listing. Photos are downloaded first; if too few arrive, nothing is created. If some fail but enough arrive, the listing is created and photo_errors lists the rest. Returns 201.

If the seller hasn't finished payout setup, the listing saves with status awaiting_payouts and goes live when they finish. You don't need to post it again.

If TeeBox takes a new listing for review, the answer says under_review, and reading it returns 404 until TeeBox releases it.

curl -X POST "$TEEBOX/listings" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" -H "Authorization: Bearer $SELLER_KEY" \
  -H "Content-Type: application/json" -H "Idempotency-Key: your-sku-1002" \
  -d '{"title": "FootJoy Shoe Bag", "brand": "FootJoy", "category": "accessories",
       "condition": "Good", "price": 40, "specs": {"itemType": "Shoe bag"},
       "photo_urls": ["https://example.com/bag.jpg"]}'

GET /v1/listings/{id}

curl "$TEEBOX/listings/LISTING_ID" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" -H "Authorization: Bearer $SELLER_KEY"

PATCH /v1/listings/{id}

Send only what changes. Spec keys you send overlay the current ones; changing category starts the specs again. photo_urls replaces every photo.

curl -X PATCH "$TEEBOX/listings/LISTING_ID" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" -H "Authorization: Bearer $SELLER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"price": 229.99}'

To sync stock, send quantity_available: the units still for sale. Sending 0 on its own ends the listing. quantity sets the total, including units already sold. Send one or the other.

curl -X PATCH "$TEEBOX/listings/LISTING_ID" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" -H "Authorization: Bearer $SELLER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"quantity_available": 2}'

POST /v1/listings/{id}/end

End a listing, for example when the item sold somewhere else. Ending an ended listing succeeds with already_ended: true. While a buyer is checking out it returns checkout_in_progress; retry in a few minutes. The API never cancels a checkout. A checkout that ran out of time no longer holds its units.

curl -X POST "$TEEBOX/listings/LISTING_ID/end" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" -H "Authorization: Bearer $SELLER_KEY"

POST /v1/sandbox/listings/{id}/sell

Sandbox only. Marks units sold, the way a real sale does, so you can test polling. quantity is optional and defaults to 1. When no units are left the status becomes sold.

curl -X POST "$TEEBOX/sandbox/listings/LISTING_ID/sell" \
  -H "X-TeeBox-Partner-Key: $PARTNER_KEY" -H "Authorization: Bearer $SELLER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"quantity": 1}'

Listing fields

You send title, brand, category, condition, price, photo_urls and the category's required specs. Optional: quantity, description, and browse_category for category other. Unknown fields are refused, so a typo never passes silently.

You get back those values plus id, url, status, currency, quantity_sold, quantity_available, photos, created_at, updated_at, expires_at, sold_at, ended_at, created_via and created_by_you. Times are ISO 8601 in UTC.

StatusMeaning
activeFor sale.
reservedA buyer is checking out. It goes back to active or becomes sold.
soldSold. Delist it everywhere else.
expiredReached its expiry date. The seller can renew it in TeeBox.
endedEnded by the seller, a tool or TeeBox.
awaiting_payoutsSaved, but hidden until the seller finishes payout setup.
needs_photosHidden because photos are missing. Send photo_urls to fix it.
under_reviewTeeBox is checking it. It can't be edited until then.

Photo URLs must be public https links to a JPEG, PNG, WebP, GIF or HEIC image, up to 15 MB and 60 megapixels each, with at most 3 redirects. Each must finish downloading within 10 seconds and open as an image, and the same picture sent twice counts once. TeeBox copies, resizes and safety-checks them. Links that need a login won't work.

Every request body is JSON, 256 KB at most. Text fields take text only: no control characters, and a title or brand needs something visible in it.

Listing rules

API listings follow the same rules, moderation and photo checks as listings made in TeeBox.

RuleValue
Price$5 or more, US dollars, at most 2 decimals
Photos1 to 10
Quantity1 to 99
Title, brand, description120, 60 and 4,000 characters at most
ConditionNew with Tags Like New Very Good Good Fair
Browse category (only for category other)clubs apparel shoes accessories bags balls headcovers shafts

TeeBox may take any listing down. It then reads as ended, and editing it, including lowering the price, doesn't reverse that. The seller is emailed the reason.

Keeping in sync

There are no webhooks in version 1. Poll GET /v1/listings with updated_since; every few minutes per seller is plenty.

  1. Ask for changes since the newest updated_at you have stored. The time is inclusive, so you will see that listing again; match on id.
  2. While has_more is true, repeat with cursor set to next_cursor. A page can be short, or empty when you filter by status; keep going until has_more is false.
  3. When a listing is sold or ended, delist it on other marketplaces. When quantity_available drops, lower your stock.

A listing that returns 404 has been removed from TeeBox. Delist it on your side. Deleted listings don't appear in updated_since results, so check listings you haven't heard about now and then.

Safe retries

Send an Idempotency-Key when you create a listing, such as your own item ID. Repeating the same key and body returns the first answer, with Idempotent-Replayed: true, and never creates a second listing. If a create fails part way with a 500, the same key and body finishes the listing it started.

  • The same key with a different body returns idempotency_key_reused.
  • Error answers below 500 are remembered too. After fixing a problem, or waiting out a daily limit, use a new key.
  • Answers of 500 or above are not remembered, so you can retry with the same key.

Responses carry RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset (seconds). A 429 for rate also carries Retry-After.

What it doesn't do

There are no endpoints for payments, payouts, refunds, transfers, orders, buyers or messages, and none are planned for version 1. Sellers handle sales in TeeBox.
